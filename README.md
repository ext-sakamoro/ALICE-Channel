# ALICE-Channel

Mutually authenticated, encrypted channels between certified devices.

Two devices run the Noise handshake `Noise_IK_25519_ChaChaPoly_SHA256` on ALICE-Crypto's X25519, SHA-256 and ChaCha20-Poly1305 (RFC 8439). Each device's certificate (ALICE-Identity, layout version 2) names its Noise static key under the master key's signature. The initiator dials a peer whose certificate it already holds: it checks that certificate against its `PeerPolicy` and takes the responder's static key from it, so the responder's static key never travels. Each side's handshake payload is an artifact signature by its certified device key, for the context `alice-channel/handshake/v1`, over SHA-256 of the handshake hash at that point and the sender's static key, and the certificate in it must name that static key.

The responder answers only an initiator it accepts. A first message made for another static key does not open, and one from a device the policy refuses is dropped; in both cases nothing is written back, so a peer without the responder's static key and an accepted certificate learns nothing from it. The receiver resolves the certificate's subject to a master key through its `PeerPolicy` and checks the certificate (issuer, validity at the policy's time, revocation), the static key it names, and the signature over its own transcript. A device without a known master, a revoked or expired certificate, or a signature taken from another session or made for another static key never gets a channel.

```rust,ignore
let mut ch = SecureChannel::connect(stream, &credential, &policy, &peer_cert)?;
ch.send(b"hello")?;
let reply = ch.recv()?;
let who = ch.peer_cert().subject();
```

The responder writes its message only after verifying the initiator, so `connect` returning means the responder accepted this side; it also checks that the responder proved the subject of the certificate it dialled (`UnexpectedPeer` otherwise). The initiator then sends one empty message on the new keys, and `accept` returns only once it has opened it (within `DEFAULT_CONFIRM_TIMEOUT`, or `accept_with_timeout`), so a replayed first message never yields a channel. `accept` waits for the first message with the same deadline: a connection that sends nothing is dropped then, with nothing written. `connect` waits for the responder's message with the same deadline (`connect_with_timeout`). A channel returned by `accept` means the peer completed the handshake, not that it is still there: if it has gone, the first operation reports it.

On the wire every Noise message is one frame: a big-endian `u16` length, then that many bytes. The prologue is `alice-channel v3`. Transport messages are encrypted under a counter nonce, so a changed, replayed or reordered message is refused. An operation that did not finish leaves the channel `Poisoned`, never out of step with its peer.

`AnonymousChannel` authenticates only the responder, for a peer that should not learn who connected: it runs `Noise_NK_25519_ChaChaPoly_SHA256` with the prologue `alice-channel anonymous v1`, the initiator sends only an ephemeral key and an empty payload, and no certificate, static key or signature of the initiator crosses the wire. The responder's side holds no certificate of its peer. The two prologues differ, so a first message of one kind never opens as the other.

The same handshake runs without I/O and without a clock for a host that handles each message in a separate callback: `Initiate::start` gives the first message, `Respond::respond` reads it and gives the response and an `AwaitConfirmation`, `Initiate::finish` reads the response and gives the transport and the key confirmation, and `AwaitConfirmation::confirm` opens it. Each message has exactly one length (48, 48, then 16 bytes); any other length, or a changed byte, is a typed error (`AnonymousError`) and the state is consumed. Deadlines belong to the host. `AnonymousChannel` is built on these state machines and writes the same bytes.

Over a transport that keeps message boundaries itself (a WebSocket, a message queue), `connect_messages` and `accept_messages` run the same handshake through the `MessageIo` trait (`send` one message, `recv` one whole message of at most a given length) with the same bytes and no length prefix. A response or key confirmation of any other length is refused, and nothing is sent when the dialled certificate is refused.

`PinnedPeer` is a `PeerPolicy` that trusts exactly one subject under exactly one master key, at a given time and against given revocation lists. `PinnedPeer::service` pins a service (subject `did:alice-service:<service>`, ALICE-Identity's service certificates); the kind of peer a policy expects is `PeerPolicy::expected_peer` (`PeerKind::Person`, the default, or `PeerKind::Service(name)`), decided by the policy and never by the certificate a peer presents. For a person the certificate is checked by the device certificate rules (`DeviceCert::verify`, `verify_artifact`), which refuse a service certificate; for a service by the service certificate rules (`verify_service_cert`, `verify_service_artifact`: the name, the subject, the 30-day lifetime bound, revocation), which refuse a person's certificate. Both hold for the certificate that is dialled and for the one a peer proves in a handshake. `PinnedPeer` expects a service when its subject is a service DID and a person otherwise. A further check can be added with the `PeerPolicy::check_further` hook (default: accept).

A host that may be evicted and restarted between two messages can suspend a `Transport` (or an `AwaitConfirmation`) to 166 bytes, sealed with ChaCha20-Poly1305 under a key it supplies (`SuspendKey`), and resume it later. Each copy names its channel (`ChannelId`, the first 16 bytes of the handshake hash, in the authenticated header) and carries an epoch. The host stores the channel id when the handshake completes; `Transport::resume` takes that id and the host's floor for the channel, refuses a copy of another channel (an earlier handshake left in a reused storage slot) or below the floor, and returns the next floor. Persisting that floor before any ciphertext leaves or any received message is acted on is the only protection against a reused nonce: an older copy is then refused. A stale copy used in breach of that rule has already reused a (key, nonce) pair, which gives away the XOR of the two plaintexts and allows forgeries under that key; the peer refuses its message, but only after the fact.

`recv_before(deadline)` (on both channel types) waits at most `deadline` for the whole of the next message, however its bytes arrive. A `Timeout` before any byte of it leaves the channel usable; a `Timeout` after part of it poisons the channel. A deadline of zero gives `Timeout` without reading, and the stream's own read timeout is set back afterwards (a channel whose stream could not be set back is poisoned).

With the `async` feature, `AsyncSecureChannel` runs the same handshake over tokio streams. Its futures are safe to drop: a dropped handshake gives no channel, and a dropped send or receive poisons the channel.

The `datagram` module runs the same handshake and identity binding in datagrams that may be lost, reordered or duplicated, with no I/O of its own: the caller sends the packets it returns and feeds back the ones it receives. Each data packet is sealed on its own under an explicit 64-bit counter, and the receiver opens each counter at most once within a window of 1024 below the highest it has opened. The initiator repeats its first packet until the response comes, the responder answers a repeat with the response it already wrote, and the first data packet that opens confirms the keys. The init carries a TAI64N timestamp inside its encrypted payload, and a `Responder` answers only an init later than the last one it accepted from that static key, so an old init replayed later starts nothing.

Every time the crate reads goes through a `Clock` (a monotonic `now` for the stream deadlines, a wall `system_now` for the datagram init label). The constructors without a clock argument (`connect`, `accept`, their `_with_timeout` forms, `Initiator::start`, `InitTimestamp::now`) use `SystemClock`, the standard library's clocks. `connect_with_clock` / `accept_with_clock` (on both channel types), `Initiator::start_with_clock` and `InitTimestamp::from_clock` take a clock the caller gives. On WebAssembly with no OS (`wasm32-unknown-unknown`) the standard library has no clock, so `SystemClock` and the constructors without a clock argument do not exist there: a host passes its own clock (in a JavaScript host, from `performance.now()` and `Date.now()`), and code that does not is a compile error rather than a panic.

## Tests

- `tests/noise_vectors.rs`: the public test vector of `Noise_IK_25519_ChaChaPoly_SHA256` (cacophony), every handshake and transport message and the handshake hash byte for byte; a first message for another static key, changed, truncated, out-of-turn, replayed and small-order inputs
- `tests/handshake_identity.rs`: two devices over TCP; unknown master and revoked certificates refused in the handshake, an expired or unknown dialled certificate refused before a byte is written; a certificate for another static key, a certificate naming another static key than the handshake used, a responder proving another subject; the signature covers the transcript and the static key; a signature relayed from another session refused; a responder that never answers, a missing, invalid or slow confirmation, a replayed first message, a receive cut mid-frame
- `tests/responder_hidden.rs`: a scanner speaking the Noise layer reads nothing back for a bare ephemeral key, a first message for another static key, or a first message from a device the responder does not accept; an accepted initiator gets exactly one frame, without the responder's static key or subject in clear
- `tests/noise_nk_vectors.rs`: the public test vector of `Noise_NK_25519_ChaChaPoly_SHA256` (cacophony); another static key, a changed, out-of-turn or truncated message, a small-order key
- `tests/anonymous_channel.rs`: every byte both ways holds no 8-byte window of any value naming the initiator (the search is shown to find a planted certificate); an unknown responder certificate, an impostor responder, the other prologue, a non-empty first payload, a first frame of the wrong length and a replayed first message are refused
- `tests/anonymous_sans_io.rs`: the state machines; every other length of each message (0 to 200 bytes) and every changed byte refused with a typed error, another static key, a data message offered as the key confirmation, and an `Initiate` talking to the blocking responder over TCP. `src/anonymous/vectors.rs`: a run with fixed keys recorded from the blocking channel before it was rebuilt, and the stream channel and the state machines both reproduce it byte for byte
- `tests/peer_kind.rs`: with one master key trusted for every subject, a person policy refuses a service certificate and a service policy refuses a person's certificate (and another service), each at the dial and at the responder of a datagram handshake; the four pairs of policy kind and certificate kind are compared on both paths; `PinnedPeer` and the default kind
- `tests/pinned_peer.rs`: `PinnedPeer` accepts the service certificate the fixture master signed and trusts only its subject; another master, an expired certificate, another service, a subject that is not a service, a lifetime over 30 days and a revoked certificate are each refused before any byte is sent; the lifetime rule also holds for the certificate a responder proves in a datagram handshake; `connect_messages` against the sans-I/O responder, against `accept_messages` over an in-memory pipe and against the stream `AnonymousChannel` over TCP, data both ways; a responder with another static key refused when the response is read; responses, first messages and key confirmations of other lengths refused
- `tests/transport_suspend.rs`: suspend and resume; the copy opened with the documented layout carries the channel id, the nonce counters and the handshake hash, and the keys are not readable in it; the same plaintext over 8 evictions never gives the same ciphertext and the peer opens every message in order; a copy below the floor refused, an eviction after a send loses the channel and not a nonce, a stale copy used anyway shown to leak the XOR of the plaintexts before the peer refuses it; an earlier channel's copy refused after a new handshake at floor 0, an edited channel id refused by the tag; every cut length, trailing bytes, another version (the previous layout included), every bit flip, a raised epoch, another host key, a wrong-length key field, an unknown or other phase and the last epoch refused with a typed error; a responder evicted while it waits for the key confirmation. A unit test shows every buffer that held the keys is zero when released
- `tests/recv_deadline.rs`: `recv_before` on both channel types; a silent peer and a peer sending one byte at a time time out by the deadline; a zero deadline reads nothing; a timeout before the first byte leaves the channel usable, one mid-frame poisons it; the stream's read timeout is set back
- `tests/datagram.rs`: the datagram mode; packets opened in a shuffled order and each only once, loss, a counter below the window, a changed or forged packet that moves nothing, packets of the wrong kind, a repeated first packet answered by the same response, a lost confirmation replaced by the first data packet, a repeated response answered by a fresh confirmation, a jump ahead that forgets only the counters it leaves, a long run past the window size, refused initiators, a replayed or earlier init refused and a later one answered, distinct ciphertexts over 600 packets, and a fixed handshake pinned byte for byte
- `tests/wasm_handshake.rs`: run on wasm32-unknown-unknown under Node in CI, and natively; keys from the host's random source; the datagram handshake and data both ways; a stream `SecureChannel` connecting and accepting with a given clock against a peer played with the sans-IO Noise layer, data both ways; a fake clock: the init label follows it and a clock that steps back is refused, a peer that trickles its bytes is cut at the fake deadline, and a cut message poisons the channel; an anonymous handshake through the state machines with the responder evicted twice (suspended bytes and the floor only), data both ways. `scripts/wasm_clock_required.py`: on wasm32-unknown-unknown the constructors without a clock and the default clock type do not compile, and the same code compiles on the host
- `tests/async_channel.rs` (feature `async`): the same over tokio; the handshake dropped at each side and direction; a send or receive dropped mid-frame; the confirmation deadline; a refused initiator reads nothing back
